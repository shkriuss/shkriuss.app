# Threat model

- **Status:** accepted
- **Last updated:** 2026-10-10
- **Last reviewed:** 2026-10-10, with the audit of that day, as the runtime dependencies and the browser permission (Grammar's `clipboard-write`) that came after the review of 2026-10-04, at the end of Phase 0, called for (§6). The review at the end of Phase 1 is still due before the phase closes.
- **Applies to:** the local-only platform (no accounts, no sync, no backend). Revisit before adding any feature that uses the network.

## 1. What we protect

| #   | Asset                                 | Why it matters                                                            |
| --- | ------------------------------------- | ------------------------------------------------------------------------- |
| A1  | User data inside each app             | Personal notes, lists, health records and similar                         |
| A2  | Backup files                          | Copies of A1 that leave the device (cloud drives, email)                  |
| A3  | Backup passphrases                    | They unlock A2                                                            |
| A4  | Integrity of the delivered code       | Code running in an app's origin can read all of that app's data           |
| A5  | Developer accounts and infrastructure | GitHub, Cloudflare and the domain registrar decide what code is delivered |
| A6  | Users' privacy                        | Which apps someone uses, and when                                         |

## 2. Actors

| Actor                                                | Trust                                   | Notes                                                        |
| ---------------------------------------------------- | --------------------------------------- | ------------------------------------------------------------ |
| Other websites, and other shkriuss apps              | untrusted                               | Isolated by the browser's same-origin policy                 |
| Anyone who sends a crafted link or backup file       | untrusted                               | Imports are hostile input                                    |
| Network attacker (for example, public Wi-Fi)         | untrusted                               | HTTPS only; the `.app` and `.dev` domains are HSTS-preloaded |
| Malicious or compromised dependency or GitHub Action | untrusted                               | Supply-chain controls                                        |
| Attacker targeting the developer's accounts          | untrusted                               | Strong account security                                      |
| Cloud storage holding backups (Drive, iCloud)        | untrusted with content                  | Backups are encrypted by default                             |
| Cloudflare (hosting)                                 | trusted to deliver our files unmodified | Sees request metadata; see R1 and R5                         |
| Coding agents working on this repository             | trusted with code, not with secrets     | May follow instructions planted in what they read; T15       |
| The user's own device, operating system and browser  | trusted                                 | A compromised device is out of scope                         |

## 3. Trust boundaries

1. **Origin** — each app (`<id>.shkriuss.app`) is isolated from every other origin, including the hub and the other apps.
2. **Code delivery** — dependencies → this repository → GitHub Actions → Cloudflare → the browser and its service worker cache.
3. **Device** — data crosses it only as a file the user exports.

## 5. Residual risks (accepted)

- **R1 — Web code delivery.** As with every web app, users trust the code served when the app loads. Someone who controls the deploy pipeline or the host could ship code that reads app data. Account security and transparency (public source, provenance, file hashes) make this harder and detectable, but cannot eliminate it. Browser-enforced transparency (WAICT) will be adopted when browsers support it.
- **R2 — Compromised device, browser or extension** can read app data. Out of scope; an optional app lock may be added later.
- **R3 — Lost passphrase** means an encrypted backup cannot be opened. This is by design.
- **R4 — Storage loss outside our control.** The user or the operating system can clear site data, and removing an installed iOS app deletes its data. Only backups protect against this.
- **R5 — Metadata seen by Cloudflare:** IP address, user agent and which files are requested.
- **R6 — Worker scripts and WebAssembly modules without integrity checks.** Browsers cannot check the integrity of worker and service worker scripts ([ADR 0011](decisions/0011-worker-trusted-types-policy.md)), nor of the WebAssembly modules that the workers of some apps fetch and compile ([ADR 0014](decisions/0014-webassembly.md)), which are in the same position. Only the app's own files can become worker scripts, and the published file hashes and build provenance cover them, but a changed worker script would run. Once the service worker controls the app, it serves worker scripts from its cache, checked against their published hashes when it keeps them, at install or, for a file kept on first use such as Grammar's module, at its first request ([ADR 0019](decisions/0019-files-kept-on-first-use.md)), and again each time it serves them, with their `Content-Type` and the build's security headers and no other header, since a script injected into a page could change what Cache Storage keeps, headers included ([service worker spec](specs/service-worker.md) §4, §6.5). The first load, `/sw.js` itself, a file that the cache has lost or that fails its check, which comes from the network until the service worker has repaired its cache (§6.4), and the files of the previous version, which only clients that still run it load, stay unchecked. A changed `/sw.js` would control the app's pages until it is replaced; it is trusted as much as `index.html` on the first load, which has no hash either.
- **R7 — Guessable passphrases.** A passphrase the user picks can be weak despite its length, and whoever holds the backup can try guesses offline. Each guess costs 256 MiB of memory, which slows guessing but cannot stop it for common phrases; the app offers a generated passphrase first. The rules count only visible characters, so padding with spaces or invisible characters makes no short passphrase pass ([backup format](specs/backup-format.md) §3.1); twelve visible characters that neither repeat, nor run along the keyboard, nor stand on the short blocklist can still be a phrase that a dictionary attack finds.
- **R8 — Compiled code of others.** Grammar runs Harper's WebAssembly module as harper.js publishes it on npm; the build does not compile it from Harper's source, and its 16 MB cannot be reviewed as code is. The package goes through the same supply-chain controls as every dependency (T2), runs only in a worker under the app's Content-Security-Policy, which gives it no network beyond the app's own origin, and the crates compiled into it are listed with their licenses in the app's `/licenses.txt`.
- **R9 — Dependencies without provenance.** pnpm's trust policy (`trustPolicy: no-downgrade`) refuses a version of a package that comes with weaker evidence of where it was built than an earlier version had, such as no provenance after versions with provenance. A package that never published provenance gets no such protection. Among the runtime dependencies, `harper.js` and React Aria's packages publish none. For them, the release-age delay, the lockfile with its hashes and the review of each update remain (T2).

**Open gaps on 2026-10-10,** found by the audit of that day. Unlike the risks above, they are not accepted: each is the maintainer's action, and stays listed until it is done.

- **G1 — The staging deploy token can write production.** Cloudflare's "Workers Scripts: Edit" covers the whole account, so the token of the unapproved staging deploy can replace every production Worker, and the production approval protects only the path that CI takes (T3, T4). Until staging has a Cloudflare account of its own ([ADR 0020](decisions/0020-deployment-accounts.md), with the owner's steps), the deploy jobs install nothing beside the token but Wrangler and its own dependencies (`@shkriuss/deploy`) and refuse to deploy a commit that `main` has moved past; what remains is any code in that closure, pnpm itself, and a workflow or `wrangler.json` change merged to `main`, which needs no second review.
- **G2 — The DNS records of T12 and T13 are not in place.** On 2026-10-10 neither zone had CAA records, a null MX, SPF or DMARC, and `www` resolved on neither, though [ADR 0001](decisions/0001-domains-and-environments.md) says it redirects. All are dashboard steps of the [setup checklist](setup-checklist.md) §2 and §3. Until then, any public certificate authority may issue for the domains, and mail forged as `@shkriuss.app` is not rejected.
- **G3 — CodeQL is not a required check** of the `main` ruleset, though [ADR 0018](decisions/0018-quality-gates-as-enforced.md) asks for it (setup checklist §3). It runs on every pull request all the same; a finding does not block the merge.
- **G4 — Five allowed commands of Claude Code's project settings take any arguments** (T15), so an agent could write a file with a redirect after an allowed prefix; the maintainer replaces them with exact entries, which a session cannot do for itself.
