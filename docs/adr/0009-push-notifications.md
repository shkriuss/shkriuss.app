# 0009. Notifications while an app is closed (Web Push)

Status: Accepted (2026-10-17). All of an app's schedules together have a
limit: [ADR 0017](0017-storage-limits.md).

## Context

Calendar reminders (and future apps) need to arrive when the app is closed.
A web app can't wake itself at a set time; only a **push message from a
server** can. That changes the "nothing leaves the device" rule of
[ADR 0006](0006-local-first-data.md), so the design keeps what leaves as small
and unreadable as possible. It must also work without Google: on GrapheneOS,
browsers like IronFox receive Web Push through **UnifiedPush**.

## Decision

- **Opt-in, per app and per device.** "Also remind me when the app is closed"
  is off until switched on. Switching it off, or **Delete all data**, deletes
  the device's data on the server. If the server can't be reached then, the
  app says so, keeps the device key (and nothing else) and tries again each
  time it's opened or back online. Notifications stop on the device at once
  (it unsubscribes without waiting for the server), and "Delete all data"
  deletes everything on the device first, so a network that hangs can't
  stop it. A request that gets no answer within 20 seconds (more for a big
  upload on a slow connection) counts as "can't be reached".
- **Shared code, separate servers.** The code lives in `@shkriuss/push`. Each
  app that uses it runs the routes in its **own** Worker
  (`apps/<slug>/src/worker.ts`, `/api/push/*`; everything else is still
  plain static files). Apps never share data or keys, the browser only talks
  to the app's own address (the CSP stays `'self'`), and PR previews get
  their own separate storage, so the whole thing can be tested before merging.
- **The phone encrypts every message** to its own push subscription
  (RFC 8291) before uploading it. The server stores and forwards only
  ciphertext; neither it nor the push service (Google, Apple, Mozilla or a
  UnifiedPush server) can read a title or time label.
- **What the server stores, per device:** the push address (a URL from the
  push service), the phone's time zone, and for each scheduled notification:
  a number to tell it apart (never the app's own id, which for an imported
  event can say where it came from), its local start time, repeat pattern
  (none, daily, weekly, monthly, yearly), last day, how many minutes before
  to notify, and the encrypted message. Its tag and the page to open are
  inside the encrypted message. A device is addressed by a random key that only the phone has
  (sent as a bearer token; the server keeps only its SHA-256 hash).
- **Repeating notifications keep working** without opening the app: the server
  computes each next time from the pattern, in the phone's time zone (so
  daylight saving doesn't shift them). The same encrypted message is sent
  each time, so its text can't say "tomorrow". The app uploads the schedule
  again at least weekly while it's used; a device whose schedule isn't
  uploaded for 13 months is forgotten, so nothing stays on the server for a
  device that stopped using the app.
- **Storage:** one SQLite-backed Durable Object per device (alarms wake it at
  the next due time), and one per app holding that app's VAPID key pair,
  generated by the server on first use and never exported or shown. No
  secrets to copy, no extra Cloudflare token permissions.
- **Sending:** messages go with `TTL` 6 hours and `Urgency: high`. If the push
  service says the subscription is gone (404/410), everything for that device
  is deleted. Busy or failing push services are retried 3 times. A message
  more than an hour late is skipped. If nothing gets through for two days
  (every message fails or is refused), the device is forgotten too: a real
  push service accepts them. One signature covers a whole wake-up (it lasts
  12 hours), not one per message.
- **Limits:** 500 scheduled notifications per device, 4 KB per message and
  1.5 MB of messages in all (so a schedule fits in one stored value; the app
  sends the soonest ones that fit), https push addresses with a domain name only (no redirects), schedule
  changes rate-limited, and at most 2,000 messages per app per day (UTC):
  past that, sending waits until 00:00 UTC.
- **Checked by the device's object:** the Worker only reads an upload, in
  one go, and passes it on; the device's object checks the rest. Reading
  and checking the biggest schedule in the Worker took more than the free
  plan's 10 ms of CPU time (audit finding B-9); an object has 30 seconds.
- **Not stored in backups:** the device key and subscription keys live under
  `shkriuss-device:` in `localStorage`, which backups skip, so restoring on
  another phone can't take over this one's notifications.

## Consequences

- Reminders arrive on time with the app closed on Android (Chrome, or
  IronFox/Fennec with UnifiedPush), desktop browsers, and iPhone/iPad when the
  app is on the Home Screen (iOS 16.4+).
- The server learns when notifications are due, how many, the time zone, and
  the push address; never their content. The privacy page says so.
- Free within Cloudflare's free plan (Durable Objects: 100,000 requests a
  day; each wake-up of a device is about two: the wake-up, and one signature
  for up to 25 messages).
- New code to maintain on the server side, covered by unit tests (encryption
  test vector, schedules, signing, request checks) and browser tests with a
  local push receiver.
- Anyone can call `/api/push/*` (that's how phones reach it), and push
  addresses can be any https server (UnifiedPush servers are), so anyone can
  upload a made-up schedule. One whose push address never accepts a message
  is forgotten after two days, and one app sends at most 2,000 messages a
  day in all. So someone determined can use up only that app's messages for
  the day (its notifications then pause until 00:00 UTC), not the Durable
  Object requests the other apps need. It can't cost money on the free plan
  and can't reveal anything. A Cloudflare rate-limiting rule on `/api/`
  slows this down ([deployment](../deployment.md)). Someone could also fill
  that app's room for schedules; then new devices wait until the junk is
  forgotten ([ADR 0017](0017-storage-limits.md)).

## Alternatives

- **One central notification server** for all apps: service bindings from PR
  previews always reach production, so it couldn't be tested before merging,
  and apps would share a key and a storage namespace.
- **Uploading only the next 60 days**: hides repeat patterns a little better,
  but reminders stop if the app isn't opened.
- **Content-free pushes** ("you have a reminder") that the app fills in: the
  service worker can't read `localStorage`, and iOS requires a visible
  notification for every push.
- **Third-party push providers** (OneSignal, Firebase SDK): trackers and
  scripts from other companies, which the project rules don't allow.
